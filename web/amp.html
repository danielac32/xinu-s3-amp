Manual del kernel Xinu AMP — ESP32-S3

Este manual describe este árbol (/home/daniel/xinu-s3-amp), no el Xinu genérico ni el port bare-metal de s3-xinu. Todos los ficheros, funciones y comandos que aparecen aquí existen en el repositorio.

El kernel se ejecuta como payload AMP en el core 1 del ESP32-S3. El core 0 queda para el loader de ESP-IDF. El arranque, las particiones y el contrato entre las dos imágenes están en Manual del loader.

Regla de oro: el kernel no inicializa PSRAM, relojes, MMU ni flash. Todo eso ya lo hizo IDF. Xinu solo valida el bootinfo, publica la ventana de PSRAM, inicializa sus tablas y arranca.

1.1 Qué es AMP

AMP significa Asymmetric Multi-Processing: dos núcleos ejecutan dos sistemas distintos, no dos instancias del mismo kernel. No hay memoria compartida gestionada por ambos, no hay un scheduler común y no hay llamadas cruzadas.

  • Core 0: IDF/FreeRTOS, dueño del arranque.
  • Core 1: Xinu, dueño del payload.
  • Comunicación actual: ninguna. El core 0 se queda en vTaskDelay().

1.2 Qué NO es

  • No es un kernel bare-metal que arranca desde la ROM.
  • No es una app de IDF que llama a Xinu como librería.
  • No es SMP: Xinu no usa el core 0.
  • No es un sistema de dos imágenes con actualización A/B.

3. Arranque, memoria y heap

3.1 Secuencia

_start (start.S)
  ├─ enmascara interrupciones y limpia CCOMPARE
  ├─ VECBASE = _xt_vector_table
  ├─ copia .rodata desde XIP a PSRAM
  ├─ copia .data desde XIP a PSRAM
  ├─ ceroa .bss y .stacks
  ├─ xinu_bootinfo = a2
  ├─ sp = _nullstk_top
  └─ nulluser()
       ├─ platforminit()
       ├─ sysinit()
       │   ├─ heapInit(_end, fin de PSRAM)
       │   ├─ thrtab, semtab, montab, bfptab
       │   ├─ mailboxInit()
       │   ├─ devtab[i].init()
       │   └─ netInit()
       ├─ enable()
       └─ create(MAIN)
            └─ main()
                ├─ open(CONSOLE, SERIAL0)
                ├─ open(TFT0), open(ETH0)
                ├─ xsh_netup("ETH0")
                ├─ xsh_telnetserver("-n 1")
                ├─ xsh_httpd("80")
                ├─ xsh_udpserver("5000")
                └─ create(SHELL0)

No existe system/boot.c ni bootsvc_tab[] en este árbol. main() llama directamente a los comandos de arranque. Si añades un servicio, edita system/main.c.

3.2 Mapa de memoria

RegiónDirecciónUso
XIP0x42100000.vector, .init, .text
PSRAM0x3D801000.rodata, .data, .bss, .stacks, heap
Pila de pánico_stacks_start.._panicstk_top8 KiB
Pila del hilo nulo_panicstk_top.._nullstk_top8 KiB
Heap_end..psram_va+psram_sizeTodo lo demás

El heap es uno solo, en PSRAM. memget, memfree, stkget, malloc, free, calloc y realloc usan la misma lista libre (memlist). No hay heap interno de DRAM ni psram_malloc separado.

3.3 Reglas de memoria

  • No pongas buffers de varios KiB en la pila de 4 KiB.
  • Usa memget/memfree o malloc/free para buffers grandes.
  • Libera con la misma longitud que pediste.
  • El heap no puede solaparse con .stacks: _end está después de las pilas.
  • psram y free muestran el estado real; mem muestra el heap del kernel.

3.4 Hilos y pilas

ConstanteValorUso

create() asigna la pila con stkget(), que sale del heap de PSRAM. Si no hay memoria, create() devuelve SYSERR.

  1. Crea el fichero en el directorio correcto.
  2. Añádelo a C_FILES en el Makerules de ese directorio.
  3. Si es un directorio nuevo, añádelo a APPCOMPS o DEVICES en

  1. Recompila.

  1. Crea device/midriver/ con miInit.c, miOpen.c, miRead.c,

miWrite.c, miControl.c, miClose.c y Makerules.

  1. Añade el tipo y la instancia en xinu.conf.
  2. Añade midriver a DEVICES en platformVars.
  3. No edites system/conf.c: se genera.

5. La abstracción del kernel

5.1 devtab[]: todo es un dispositivo

Xinu no llama a w5500Read() desde la red. Llama a read(ETH0). Cada entrada de devtab[] tiene un bloque de funciones:

struct devsw {
    int  (*init)(device *);
    int  (*open)(device *, ...);
    int  (*close)(device *);
    int  (*read)(device *, void *, int);
    int  (*write)(device *, const void *, int);
    int  (*getc)(device *);
    int  (*putc)(device *, char);
    int  (*control)(device *, int, long, long);
};

Ventajas:

  • el shell, la red y la JVM no conocen el hardware;
  • se puede sustituir un driver por null en xinu-test.conf;
  • el mismo código de alto nivel funciona en placa completa y en pruebas.

5.2 Syscalls

Las llamadas al kernel (create, wait, signal, sleep, read, write, open, close, control, kill, receive, send) son funciones C con syscall en la cabecera. En este port no hay cambio de anillo: todo corre en modo supervisor. syscall es una marca de intención, no una instrucción de trampa.

5.3 Concurrencia

MecanismoUso típicoDato
SemáforoContar recursos o esperar eventoNo
MonitorExclusión mutua recursivaNo
MailboxCola de trabajo de un servicio1 int
send/receiveMensaje punto a punto a un tid1 int

Reglas:

  • no duermas con un monitor cogido;
  • no llames a wait, sleep ni lock desde una ISR;
  • un lock por cada unlock;
  • si el mensaje es un puntero, define quién libera.

5.4 Context switch

El ESP32-S3 usa ABI CALL0: no hay ventanas de registros. ctxsw.S guarda a0, a2..a15, PS, PC y el stack pointer. Por eso el cambio de contexto es un save/restore plano, no un spill de ventanas.

6.7 lib/

lib/libxc/ es la libc mínima: printf, malloc, free, str*, mem*, qsort, doprnt, etc. No se enlaza libgcc porque el toolchain solo trae una versión windowed, incompatible con CALL0. La coma flotante está en system/softfloat.c.

6.8 mailbox/

Implementa las mailboxes: array circular, semáforo de lleno y semáforo de vacío. Se usan en ARP e ICMP para no bloquear el hilo de recepción.

9.3 GAT: Gestor de Archivos y Terminal

En este árbol no existe una librería C llamada GAT. Lo que sí existe es el módulo que llamamos GAT (Gestor de Archivos y Terminal), formado por:

  • shell/xsh_httpd.c: servidor HTTP y ficheros estáticos;
  • shell/httpapi.c: API JSON de archivos y ejecución;
  • shell/webterm.c: worker, monitor, semáforo y MEMTTY0;
  • web/index.html: interfaz de usuario con gestor de archivos y terminal.

Flujo del terminal:

navegador
  └─ POST /api/exec
       └─ api_exec() → webtermSubmit() → signal(jobsem)
            └─ webshell → webtermRun()
                 ├─ builtin: ejecuta en webshell
                 └─ externo: create(hijo) con stdout/stderr en MEMTTY0
  └─ GET /api/job?id=N
       └─ api_job() → webtermStatus()/webtermSnapshot()

Si por "GAT" te referías a otra librería, no está en este repositorio. La capa de soporte del kernel es lib/libxc; la abstracción de dispositivos es devtab[].

  1. Copia compile/platforms/esp32s3 a compile/platforms/miplaca.
  2. Ajusta platformVars: toolchain, flags, APPCOMPS, DEVICES.
  3. Ajusta ld-amp.script: direcciones XIP/PSRAM y .stacks.

11.3 Qué no se puede cambiar a la ligera

  • El ABI CALL0 y el layout de ctxsw.S.
  • El contrato bootinfo sin sincronizar loader y payload.
  • La dirección XIP 0x42100000 sin cambiar el loader.
  • El alias PSRAM 0x3D801000 sin cambiar el linker y el loader.
  • El heap único: si añades otro allocator, rompes free/malloc.

12. Simple JVM

12.1 Qué es

Es un intérprete de bytecodes Java, no una JVM completa. Carga un .class, parsea constant pool, campos y métodos, ejecuta <clinit> y main(String[]). Conserva el paquete esp32p4.* para que las clases del P4 corran sin recompilar.

12.2 Estado y memoria

ElementoValor
Pila del hiloJVM_STK = 65536 B
Slots de heapJVM_HEAP_SLOTS = 2048
Locals por frameJVM_MAX_LOCALS = 16
Profundidad de llamadasJVM_MAX_CALLS = 32
EstáticosJVM_MAX_STATICS = 64
Pila de operandos500 entradas

Cada ejecución crea una instancia Jvm en PSRAM con jvm_state_new(). El estado incluye pools, locals, heap, estáticos y frames. La VM es reentrante: varias tareas pueden ejecutar Java a la vez, cada una con su instancia.

12.3 No hay GC

No hay recolector de basura. heap_new_slot() busca un slot libre, pero nada los libera durante la ejecución:

  • objetos, arrays, Strings y StringBuilders ocupan slots hasta el final;
  • jvm_state_free() libera todo al terminar la tarea;
  • free_pools() libera atributos de métodos al final;
  • no hay System.gc(), finalizadores, compactación ni referencias débiles.

Consecuencia: un bucle que crea objetos sin parar agota los 2048 slots y llama a exit(6) (en el target, mata la tarea). Para apps largas:

  • reutiliza objetos;
  • evita new dentro de bucles;
  • usa arrays de tamaño fijo;
  • no confíes en que la memoria se recupere.

12.4 Natives

Los natives son funciones C registradas en jvm/java_lib.c:

{"esp32p4/RGB", "set", esp32p4_rgb_set}

La firma es:

int mi_native(StackFrame *stack, SimpleConstantPool *p, char *type);

Los argumentos están en la pila de operandos; el último argumento está en la cima. Se leen con popInt(stack) y se devuelve con pushInt(stack, valor). El tutorial completo está en Manual de natives.

12.5 Limitaciones

  • No hay Thread real; Thread.sleep se mapea a Sys.sleep.
  • No hay PMIC en el S3; esp32p4.PMIC no existe.
  • LVGL está en fase 2.
  • Sys.run() crea otra tarea JVM; no está probado en todas las apps.
  • La JVM necesita FAT/SD para cargar .class.
  • date puede mostrar 1900 porque el RTC no se inicializa.
